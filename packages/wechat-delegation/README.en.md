# WeChat delegation and human takeover — security rewrite in progress

The intended product lets the authenticated owner select a normal WeChat friend or group, choose a cat and speaking style, authorize proactive messages/replies, and take over at any time. It does not substitute a bot or desktop OCR for that journey.
Local desktop detection uses a separate owned read-only helper, isolated from the credential service. The connection card distinguishes desktop observations from the plugin connection. Installation, running state, signature and permission checks work before account preparation. Only a supported version and explicit application-menu evidence allow a logged-in UI observation; missing permission or unknown evidence stays undetermined. System accessibility prompting requires a separate owner confirmation. Real permission attribution and positive menu matching still need on-device validation. Detection never imports the desktop session or starts authentication or sending.


This branch is an internal development candidate, not an accepted installation. The restricted native service, private stdio client, final sender deadlines, Host stop/renewal ordering, durable authentication intents, sync baseline/reset and exact canonical delivery inspection are implemented. The panel exposes explicit resume/cancel, synchronization state, system Keychain authorization and evidence-bound first-initialization recovery. Explicit per-login LAN consent is implemented; interactive system validation and final real-account acceptance remain open. `accountServiceReady=false`. The running plugin has not been replaced; no real account login/send, merge or publication is claimed.

The bundled `clowder-wechat-link` replaces the general Agent WeChat HTTP daemon. Its fixed MIT protocol subset has no generic URL/shell, secret export or old desktop-profile import. Credentials/messages persist in an encrypted Vault; the key uses a macOS file Keychain application ACL, not a claim of Secure Enclave protection. The owned child receives private pipes and no owner environment. Model sessions receive only authorized persona/goal/chat text, with no account secrets, QR or direct sender tools. The Host owns policy and model selection; the native service owns account transactions, current relationship verification and final submission. Durable takeover/expiry fences queued and in-flight work; unknown outcomes retain their original key and are never automatically resent. User chat/control/send history has no default TTL.

Tests use isolated synthetic remote peers and stores. Actual Keychain checks use newly created private synthetic Keychains; the authorization backend is exercised only on an already trusted, unlocked synthetic item, without a real dialog. Physical bundled-executable checks use offline mode or reject missing state before opening default Keychain entries. An actual DYLD injection canary verifies hardened runtime protection. These checks do not prove real account compatibility, message delivery or interactive system behavior. Current native bytes target macOS Apple Silicon, minimum/tested macOS 26.5, with an ad-hoc hardened runtime signature and no Apple Team or notarization. Cross-process upgrade trust still requires explicit system authorization and real validation.

Neither this partial provenance nor green tests constitutes overall security acceptance.

No instructions to replace the owner's currently running plugin are offered until the full candidate and explicit real-account/release authority are available.
