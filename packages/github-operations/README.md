# GitHub 协作

简体中文 · [English](README.en.md)

`@clowder-ai/github-operations` 把 GitHub 动态跟踪和社区协作放在一个插件里：跟踪 PR 审查、CI 检查、合并冲突、Issue 和评论，汇集仓库动态，并提供社区分诊与待确认的 Issue 草稿。

## 开始使用

1. 在 Clowder AI 设置中安装插件。GitHub CLI `gh` 应在运行 Clowder AI 的机器上完成登录。
2. 已有本机 `gh` 登录时无需填写令牌；否则在「GitHub 访问令牌（可选）」填写。保存配置后点击「测试连接」，确认当前 GitHub 账号。此检测只读账号，不启动轮询，也不保证所有仓库权限。
3. 启用插件，使用已安装的 GitHub Operations skill 和工具登记跟踪。配置保存、连接成功与插件实际运行是不同状态；跟踪和后台轮询需要插件实际运行。

其余配置按需填写，不是安装前置步骤：

| 配置 | 用途 |
| --- | --- |
| 通知作者白名单（可选） | 只接收指定 GitHub 登录名的评论和审查通知；留空不额外限制。 |
| 通知作者黑名单（可选） | 忽略指定登录名的评论和审查通知，不区分大小写，黑名单优先。CI、合并和冲突状态不受影响。 |
| 仓库 Webhook 签名密钥（可选） | 仅在启用仓库 Webhook 时配置；使用 Host 提供的准确回调地址。定时跟踪无需此项。 |
| 公开 Issue 草稿允许的仓库（可选） | 允许发布 Issue 草稿的 `owner/repository`，以逗号分隔；留空时不允许新建或发布这类草稿。 |

普通使用的五项配置全部可选；“接续旧跟踪”和“旧跟踪恢复状态”仅供已有记录迁移，新安装留空即可。内部策略、遗留 `mcpToken` 和社区简报接收坐标保留原声明及已存值，不在普通设置展示。草稿由插件保存，发布需要支持该草稿的 owner 认证预览；迁移后的反馈入口可能只显示已保存摘要，不能据此声称发布流程已完成；设置页不再提供草稿或简报操作按钮。已有草稿、密钥和轮询记录不删除。新安装不要求导入旧配置、旧权限或历史游标。

## 本地更新与验收

新登记的 PR / Issue 跟踪、条件、游标、回执和通知队列由插件私有存储维护。插件定时拉取变化，生成普通消息，经现有消息路由投递；新订阅不创建 Host 任务，也不读取会话正文。接续旧 Host 等待时，单独保留原任务、owner、thread 与 generation，投递和终态继续核对原绑定；这条迁移路径需要声明的 task.read / task.write，不把新订阅转成 Host 任务。登记身份由原生入口认证；投递目标由消息接口校验。社区流程需要线程摘要时，只使用当前用户可见的元数据。新订阅不调用 Host Task；具体权限以安装页和插件声明为准。

Host [通用修复提案 #232](https://github.com/mindfn/clowder-ai/pull/232) 单独处理插件 MCP 项目同步与空绑定界面；GitHub 专用权限和草稿界面修改不作为本插件前置。MCP 工具缺失时核对项目能力同步；工具已出现但登记失败时，用 `github_list_tracking` 查看持久诊断的阶段和错误码，不从 502 推断 PAT 有误。首次登记会读取 GitHub 起始状态，随后由插件定时轮询。同一 PR / Issue 在不同认证会话中使用独立私有订阅，旧取消历史保留。未知结果重用相同 registrationId 和参数。登记成功后才触发要测试的在线 review。

作者名单以逗号或空格分隔，不区分大小写，作为登记条件之外的额外过滤。过滤不修改 GitHub 事实或收集游标；放开名单不会补发此前过滤掉的历史通知。已生成的持久通知队列保留用于失败恢复。

本地候选包不需要等待 catalog 上架。交付证据提供 exact archive、SHA256 和 SHA512 SRI；核对后解包，在插件设置的「从目录安装」选择解包后的 `package` 目录（有 `plugin.yaml` 和 `package.json` 的那层）。选择同一 pluginId 的本地目录会走原实例更新路径，保留实例、密钥和持久跟踪状态；无需先卸载。首次离线安装可直接上传自包含 `.tgz`。

**已有 catalog/npm 安装请使用目录更新**：当前 Host 的 archive 更新要求新旧 provenance 同为 local-archive，直接上传可能返回已安装冲突。不要为绕过冲突卸载旧实例。目录方式可替换 catalog/npm 安装；若原实例启用，Host 会按既有生命周期暂停并恢复该插件。

更新后核对版本 `0.1.0-alpha.28`：核对可选配置与旧跟踪恢复入口，不出现草稿操作按钮。保存并测试连接，再确认插件运行状态。让猫调用 `github_list_tracking` 读取既有登记，再对已登记 PR 使用 `github_inspect_subject` 读取本地观察；必要时对一个明确授权的 PR 登记跟踪，保持相同 registrationId 重试。`github_refresh_pull_requests` + `github_repository_observations` 可验证仓库 provider 读取。首次登记只建立基线，不能把“暂无新通知”当作失败；观察下一次真实审查/CI 变化再确认消息投递。

等待较多时，后台轮询分轮处理并保存续扫位置。慢请求或模块重启不会清除旧条件、基线和待投递回执；一次轮询完成不代表所有等待都已检查或已经产生通知。

回滚时选择原验证包的解包目录更新，不清除实例、配置或历史。真实账号的登记与通知仍须在实际安装后验收，包内隔离测试不等同于运行实例已经恢复。

恢复暂停期间，若一个尚未原生绑定的 Host 等待已经由原任务正常关闭，owner 的 recover 会将冻结副本保留为惰性历史，不重新激活该任务。旧快照与计划摘要保留；身份或活跃状态漂移、已有绑定意图、未结投递仍会阻止放行。

## 跟踪 PR 和 Issue

插件声明了 `github-tracking` 原生 MCP。猫通过当前工具说明使用：

- `cat_cafe_register_pr_tracking`：登记 PR 跟踪。
- `cat_cafe_register_issue_tracking`：登记 Issue 跟踪。
- `cat_cafe_unregister_tracking`：仅取消当前认证用户、猫在当前线程的指定订阅，保留历史；不影响其他猫或线程。

登记需要仓库、编号和唯一 `registrationId`。响应不明时，使用相同 ID 和相同参数重试，不要另建一份跟踪。当前猫、thread 和 invocation 身份由 Host 认证，不是工具参数。

第一次登记只记录当前基线，不补发一串历史动态；之后符合条件的变化才投递成普通消息。仓库收件箱另行登记仓库。没有登记的对象不会因为安装插件就被定时轮询。页面按需读取 PR 标题是独立的只读操作，不会登记跟踪或刷新仓库索引。

关闭或合并的对象在最终采集和投递完成后退出跟踪。采集失败不推进游标；待投递消息保留重试。禁用插件会取消正在进行的 provider 工作并等待清理，之后重新启用仍使用持久状态恢复。

## 社区分诊与发布

审查记录保存当前 GitHub 修订与审查结果，不改变 Host 的任务执行责任。需要 guardian 时，调用方显式提供 `guardianCatId`；插件保存业务邀请与检查清单，签署核验当前调用者。反馈卡通过普通草稿创建动作传入标题、正文和仓库，返回的草稿由插件私有状态管理。

Community 页面可以读取仓库事实、查看草稿和进行已声明的协作操作。Issue 草稿会先经过整理和确认，发布仍需明确操作及允许的目标仓库；空白发布仓库配置不能被绕过。

如配置了 narrator 的猫和 thread，手动分诊提交会保存固定目标和简报，再由既有调度投递。修改目标会暂停原投递，不会把旧简报改发给新目标。恢复原配置后可重试；启用配置不会自动唤醒历史事项。

外部审查结果通过 `github_record_external_review_verdict` 提交。`pending_verification` 表示结果已保存，**不表示审查送达或租约完成已被批准**。缺少可信发布者关联时，验证会返回 `insufficient`，不能仅凭 GitHub 上出现一条审查就宣称完成。

## 页面上的能力名称是什么意思

MCP、skill 和调度是用户或猫直接使用的能力；插件也需要声明与 Host 页面、消息及验证流程相连的接点。

| 名称 | 实际作用 |
| --- | --- |
| 工具 / `github-tracking` MCP | 登记、读取和停止跟踪，以及已声明的 Community 操作。 |
| Skill | 说明这些工具的适用场景和用法。 |
| 调度 | 定时检查已登记的事项，恢复未完成的采集与投递。 |
| `community-http-01` 到 `29` | Community 页面的内部 HTTP 路由编号，不是要求用户去 GitHub 配置 29 个 Webhook。 |
| `github/events` | 可选的外部仓库 Webhook；检查原始请求的 HMAC，只接受已登记仓库。 |
| `github/pr-title` | 页面展示需要时读取最新 PR 标题，不改跟踪状态。 |
| `github-notification`、`github-wait` 身份 | 标记通知和等待的插件来源，不是新的 GitHub 账号，也不是调用者授权。 |

这些接点都属于**同一个插件**，共享一份 `plugin.yaml`、pluginId、版本和能力声明；不是多个插件或新增配置步骤。本包没有声明 limb。内部编号是否出现在普通能力页，由 Host 的展示层处理，不应通过删掉实际接线来改变功能。

## GitHub 认领与宿主通知

GitHub Issue 的 Assignees 是当前认领事实，事件时间线保留认领和取消历史。
可以直接在 GitHub 添加或移除本人 Assignee；无需通过 Issue 工作台生成特殊评论。

在此 GitHub 连接的设置中填写 `认领收件仓库`、`认领通知对话`、`认领通知协调猫`，
再开启 `接收我的 GitHub 认领`。系统约每分钟核对当前登录账号的 Open 认领；
首次启用也补收已有认领，撤销、关闭和重新认领分别通知。`GitHub 认领收件状态`
提供 `查看认领同步状态` 与 `重试认领同步`。读取失败保留进度，不将失败当作取消。

通知通过宿主普通消息路由到本人对话并唤醒协调猫；接收方不用安装 Issue 工作台。
猫先通知 co-creator，按本人接手或既有适用授权进入宿主 Task/开发流程；
外部负责人变化本身不授权代码执行。取消时通知原宿主保留成果、处理暂停或交接。
修改目标会为新目标补收当前认领，旧通知保留原目标与去重状态。

## 权限与恢复边界

Host 管理安装、授权、thread 访问、存储机制和普通消息/唤醒；插件管理 GitHub 读取、过滤、跟踪和社区业务。安装不等于自动同意所有权限。

插件使用已配置的 GitHub token 和 Webhook 密钥访问账号、核验请求；私有保存跟踪状态、游标、去重记录与投递进度，以便恢复未完成的事项。

工具参数、评论、仓库文本及消息元数据都不能充当当前猫身份、owner 权限、批准或发布授权。原生 MCP 通过 SDK 的认证调用通路进入本插件；不会恢复已退役的外部 GitHub MCP 集成。

PR 轮询每轮最多接纳 20 个等待，使用共同的 CI 基础事实；每个 PR 的深入读取有独立 10 秒界限，整轮预算为 30 秒。失败保留原基线和 generation。中途取消或重登记会再次校验，未完成的通知可恢复；这些包内回归不是 Host 真实旅程通过的替代证据。

发行备注：当前是未公开发布的本地候选，真实账号旅程与公开分发需分别验收。

## 接续迁移前的 GitHub 跟踪

如需接续已有观察历史，在激活替代实例前，将“接续旧跟踪（可选）”设置为
`import-only`。采集、Webhook 和注册都会暂停；普通注册会取新基线，不能替代旧等待迁移。
恢复面板的状态与来源覆盖按钮会显示进度和缺失字段。沿获审的 owner 恢复流程导入，按提示由
原负责猫在原线程确认绑定，全部核验后再明确释放一个采集者。旧投递有歧义时继续暂停。
[恢复契约](../../docs/plans/2026-10-21-github-cutover-preparation.md)列明运维入口与回退边界；
代码和产物可运行不代表已经取得正式安装、持久授权或恢复完成。
