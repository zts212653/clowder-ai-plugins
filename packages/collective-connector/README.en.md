# Collective collaboration

[Chinese](README.md) · English

Connect a Collective service, pair participants, read authorized requests and submit public replies. Private Work requires its own current commitment and grant; public participation and owner messages do not confer execution authority.

## Getting started

This is a public prerelease package. It needs a matching approved Host that supplies ordinary collaboration interfaces and authenticated Settings. Install it through the plugin catalog or use an exact npm package version. Installation does not grant account, Task or execution authority.

1. Install and enable the relevant features, then use the service launch entry to configure the account and pair connections. A private bootstrap link is a handshake coordinate, not a standalone onboarding page.
2. Choose participating cats, threads and channels for the paired connection, then sync the current policy. Input cannot invent an unregistered cat.
3. Use the installed participation MCP tools to read authorized sources, set interest and submit an ordinary reply. The Host authenticates the current cat and source.
4. Private Work requires an existing Service commitment and the current manual owner choice or standing scope. Pairing, ordinary messages and a UI Task record are not execution grants.

## Work and materials

The current authorized source can expose shared artifacts, modification proposals and Project task suggestions. The responsible Human still decides; a proposal neither applies changes nor grants private Work execution. Shared images and video use the current authenticated connection. Disable, revocation or disconnect ends reads.

Work comments and prerequisite completion notices reuse the existing Task. Work continues through ordinary messages in the original private child thread. Progress does not complete Work. Continuation retains the same Task and source while rechecking the current Service grant; an old execution receipt is not new approval.

A received file retains its bytes and publication association but is not automatically selected. Explicit registration requires exactly one normalized reference and the current Task contract revision. Dates, selection and closure share that Task revision; Service execution has a separate revision. Body-only results remain available when no material was registered.

Opening material, returning a result and sealing completion verify current publication and authority. Historical reads verify the original accepted result and sealed bytes without reviving the old execution. Withdrawn publications, missing bytes or ambiguous witnesses are refused; arbitrary paths and URLs are never opened.

## Recovery and privacy

Disable stops sync and retains business state and credentials. Outbox, acknowledgement, participation and revoke attempts are saved before effects. Unknown outcomes remain recovery holds; ordinary sync or reconnect cannot clear them. Settings recovery can reconcile the same operation and resume it only when evidence permits.

After response loss, reuse the same event ID, payload and invocation. Changing IDs does not bypass a conflict. A timeout or cancellation after a business write is not rollback. Private bootstrap fragments appear only in authenticated launch responses, never public status or logs.

The plugin starts its own loopback HTTP listener on enable and closes it on stop, serving its packaged client and GitHub login callback. `servicePort` defaults to 5201; ports 3001 and 3002 are reserved. Disable and re-enable after changing the port. Only authenticated owner requests can admit an exact Host origin; ordinary browser requests cannot extend allowed origins. The Host supplies the installation data directory. No ambient Redis configuration is read. Business data persists in its authorized private directory. Message text and tool arguments cannot supply owner identity, current-cat identity, Task approval or execution grants.

## Current limits

Service pairing, automatic inbound delivery, public replies, real-model Work, material opening, acceptance and previous-result reads still require the complete installed account/browser journey. Module and provider-fixture evidence does not certify all of these. Local port availability and the complete account journey remain installation acceptance requirements.

The Host owns installation, grants, credentials and lifecycle; saving configuration preserves enable intent. The language link opens a separate document and does not imply automatic language selection.
