### 需要兑现的行为

1. **接入后的首轮分析**：在来源接入成功、分析目标可用的条件下启动一次初始批次。
   刷新页面、轮询、服务重启和同一接入重试恢复原批次，不重复执行整批。
   不能把历史静态分类文件或标题关键词候选当成本次深度分析的完成证据。
2. **持续可纠正**：人工可以修改类别与分析；也可以选择一只可用猫发起新一轮分析。
   分类展示、分类筛选和类别派工规则应使用同一个当前有效结果；旧版本及其来源保留。
   人工保存的判断不被后台结果静默覆盖。原 Feature 绑定与来源状态约束继续成立。
3. **人工派工**：不强制先请猫分析；用户选择当前组织成员并确认具体问题的分派。
   实际写入方式沿用既有“通知成员接手 / 设置 GitHub 负责人”，与手动或自动模式分开。
4. **自动批量派工**：由已配置并启用的规则处理待分派问题，能使用已有有效分类，
   不要求为了派工重新调用模型。保留当前规则优先级：组织成员自提优先本人，
   再匹配 Feature 或类别分工；未命中、冲突、已有其他负责人或来源变化时保留待判断。
   每条问题记录匹配依据和真实结果；部分失败可恢复，重试不重复发布。
5. **两条流程各自可用**：分类不会自行开启派工策略；人工改类不立即改写已存在的
   GitHub 负责人。分类进行中、分类完成、派工成功、对方接手和猫实际开工分别展示。

## 原始诉求与目标

用户希望分类后把 Issue 分配给团队成员修复，主动通知成员各自的猫猫团队；
即便分配时对方离线，启动团队后也能监听到。成员各有自己的 GitHub 账号。
问题采用 10 分制优先级，用户给出的明确锚点是“阻塞猫猫咖啡店运行”为 8–9 分。

完整旅程：按类别找到问题 → 查看影响并评分 → 选择成员并分配 →
对方团队在线收取或启动后补收 → 接手、修复并回报 →
工作台看到进度、修复材料和验证结果。

## 已确认需求与草案假设

已确认：分类后分配、成员独立 GitHub 身份、主动通知、团队启动后接收、
个人问题队列按优先程度分级、10 分制与运行阻塞的 8–9 分锚点。

以下作为第一版建议，尚未视为用户已批准的执行策略：

- GitHub Assignees 作为共享成员分配的事实源；工作台展示同一份分配。
- 每个问题有一位明确主负责人，可带协作者；不自动删除已有多人分配。
- 问题有一个团队共用的优先分数；每位成员的队列据此排序。
- 团队默认自动收取和提醒，接手后才进入修复执行。自动开工需要成员自己的明确策略。
- 模型可建议优先级和负责人，由有权限的成员确认；不把分类结果直接当作优先级。

## 1. 成员身份与分配

- 成员以各自 GitHub 账号连接工作台，显示账号、可访问仓库及其团队接收入口。
  账号凭据由各自环境管理；GitHub 用户身份与本地猫身份分别绑定。
- 在列表、分类结果和问题详情中选择负责人，支持模糊搜索、单条与批量分配。
  批量操作先展示选中问题、目标成员、优先级与变更范围。
- 支持转派、取消分配、协作成员和分配说明；保留操作人、时间和变更历史。
- 分配前核对仓库权限与成员是否可被分配，写入后读回。
  单条失败明确标出，不把整个批次显示为成功；重试不重复创建任务或通知。
- 默认待修复队列展示 Open 问题。Closed 问题可作为回归验证任务显式纳入，
  或按本仓仍复现的证据建立对应工作；不因本地派工自动重开 GitHub Issue。
- 已绑定 Feature 的问题仍留在“随 Feature 处理”分类，支持按 Feature 查看和选择。
  Feature 负责人可作为分配建议；批量分配成员必须能看清实际影响的问题。

## 2. 主动通知与离线补收

- 分配成功后，接收方已运行的团队能发现新增分配并主动提示。
  提示包含仓库/编号、标题、分类或 Feature、优先级及原因、分配人、处理目标和问题链接。
- 对方未启动时，分配和待收取状态持久保留，不要求双方同时在线。
  团队启动或恢复连接后，主动核对当前账号在获准仓库中的分配并补收。
- 首次启用也必须展示此前已分给自己的未完成事项；后续启动恢复接收进度，
  同一分配版本只形成一个有效待办。可以汇总提醒，避免历史问题逐条刷屏。
- 接收侧提供“我的待处理”入口，并投递到成员配置的团队收件箱/协调猫。
  该成员的团队再决定由哪只猫承担任务，分配方不需要知道对方本地猫 ID。
- 断网、限流、凭据失效或仓库失权时显示同步失败与上次成功时间，
  保留可恢复状态，不显示“已收到”或空队列冒充成功。
- 处理优先级升高、转派和取消分配。接手前重新核对当前分配；
  已在执行的旧负责人收到变更提示，不自动删除其成果或强行中断运行。
- GitHub 通知可以辅助提醒；其已读/未读状态不能代替团队接收和接手回执。

## 3. 10 分制优先级

以下是建议分档；其中“运行阻塞 8–9 分”来自用户，其余锚点待讨论。

| 分数 | 建议等级 | 判断锚点 |
| --- | --- | --- |
| 10 | 紧急事件 | 正在发生数据损失或安全事故等，需要立即止损 |
| 9 | 严重阻塞 | 核心运行链路普遍不可用，缺少可行替代路径 |
| 8 | 高优先 | 某成员/环境的核心使用链路被阻塞，例如无法启动、对话或派猫 |
| 6–7 | 高影响 | 核心能力明显受损，但存在可用的临时处理办法 |
| 3–5 | 常规 | 局部功能缺陷，主要工作流程仍可继续 |
| 1–2 | 优化 | 体验、布局、文案等改善，当前不阻塞工作 |
| 未评分 | 待研判 | 尚缺影响证据；不自动当作低优先级 |

- 评分要记录受影响能力、人群/环境、阻塞情况、替代路径和证据。
  相同“界面问题”也可能阻塞所有操作，不能按分类名称固定分数。
- 模型建议附理由和依据；证据不足显示待研判，人工可调整并留下修改理由。
  分数表示处理紧迫程度，不表示模型确信程度。
- 分数随影响变化可重评，调整者和时间可追溯；收到高优先升级时更新提醒。
- 每位成员的队列默认高分优先，同分按等待时间排序；未评分单列待研判。
  修复难度、工作量和被依赖情况单独显示，避免“难修”直接导致严重问题降分。
- 分类、Feature 绑定、Open/Closed、分配状态和优先级分别表达各自含义。
  高优先阻塞问题即使属于一个长期 Feature，也须能独立浮到队列前面。

## 4. 工作台与接收方体验

| 入口 | 应看到和操作的内容 |
| --- | --- |
| 分类列表/问题队列 | 负责人、优先级及理由摘要、接手状态；按成员、分数、类别、Feature、来源状态筛选 |
| 分配操作 | 搜索成员、选择问题、填写处理目标、确认分配及查看逐条结果 |
| 成员视图 | 每个人待接手、处理中、受阻、待验证的问题；高优先项优先展示 |
| 问题详情 | 评分依据、当前负责人、分配历史、团队接收回执、执行进度、PR/验证材料 |
| 接收方团队 | 启动后的待办摘要；接手、退回说明、受阻反馈；点击进入对应问题和工作线程 |

共享分配的状态至少区分“分配成功 / 对方团队已收取 / 已接手”。
执行阶段再区分“处理中 / 受阻 / 待验证 / 已验收”。没有接收回执时显示“待收取”，
不能只凭 GitHub 写入或发出提醒就推断对方在线、已读或正在修复。
GitHub 已关闭与本仓验证通过继续独立展示。

## 5. 共享与权限边界

- 分配、优先级及接收回执必须能跨成员环境读取，不能仅存于分配者本地。
  共享载体、修改权限和冲突规则在设计阶段确定；不假定 GitHub 自带 1–10 分字段。
- GitHub 管理成员分配事实；各成员 Host 管理其猫、执行任务和真实接手状态。
  工作台保存关联和投影，不复制一套 Host 执行任务权威。
- 成员本人控制团队接收入口和自动执行策略。共享通知只包含其有权读取的内容，
  内部分析和未公开资料不能随公开 Issue 通知自动外发。
- 当前工作台以 READ 和本地记录为边界。新增远端分配、共享优先级或回执写入，
  需要独立列清仓库与动作权限；本轮需求草案不执行这些写入。
- 现有 GitHub Operations 候选已有持久跟踪、轮询和消息投递，可作为复用方向。
  它的现有“首次登记只建基线”不能直接满足本需求的首次启动补收，仍需验证/扩展。

## 6. 完成判据

1. 两个独立 GitHub 账号、各自团队环境完成真实旅程：A 分配一个 9 分问题给 B，
   B 离线；B 启动后收到问题和分数理由，接手后 A 能看到回执与进度。
2. B 在线时收取新增分配；连续重启、重复同步和请求重试不会重复创建同一工作。
3. B 能在个人队列看到 9、8、5 分问题按顺序排列，未评分显式进入待研判；
   分数变化可跨环境同步并追溯。
4. 105 条已有 Feature 分类保持原归属，仍可分配和评分；Feature 视图与个人队列指向同一问题。
5. 转派、取消、GitHub 外部改动及两个环境同时处理时，最终负责人能对齐，
   不让过期分配开启新工作，也不丢失已写成果。
6. 断网、授权失效和部分失败均显示真实状态；恢复后补收成功。
   仅写入 GitHub、生成通知或通过合成测试均不能代替双账号端到端验收。
