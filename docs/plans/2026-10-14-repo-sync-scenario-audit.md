# PR #77 使用场景与恢复边界排查

原需求是单向接收外部更新、保留 commit / Issue / PR 来源与内部对应，允许按 tag 接收并保留声明的内部文件差异。同步由确定性代码执行，平台审核仍打开具体 PR。用户反馈的重点包括 SSH 与网页地址不同、Windows 文件占用、错误引用无法退回、自动 PR 未接通、大量文件和异常时不知道下一步如何处理。本轮继续在同一 feature 分支交付，不创建新 PR。

## 本轮确认的问题与处置

| 场景 | 原行为 / 风险 | 本轮处理与恢复入口 | 验证 |
| --- | --- | --- | --- |
| 自动 PR 引用已撤销，随后恢复 | 旧回执重新登记，违背人工撤销 | Git 与命令适配器都拒绝重登记；当前步骤只补登记平台已有 PR | Git / adapter 测试；新浏览器旅程 |
| 人工纠正为另一 PR，旧 Git 回执仍存在 | 准备恢复覆盖人工纠正 | PR_MAPPING_CONFLICT，保留纠正后的引用及创建次数 | 原失败测试后修复 |
| 中间执行记录保存失败，后续写恢复正常 | promise 链一直失败，最终记录也丢失 | 每次写独立恢复，最终快照包含完整阶段；不重跑业务 | task-durability |
| 任务记录已写但 latest 索引写失败 | 留下没有真正执行的 RUNNING 记录 | 命名任务改为 FAILED，标记业务未执行；由原执行器只补存 | task-durability |
| 业务完成，最终执行记录仍在保存 | 界面提前显示完成 | 显示“保存执行记录”，最终保存结束后才公布普通终态 | 确认 RED 后 GREEN |
| 外层 PR 核验内调用连接检查 | 外层仍显示运行；内层重新开放取消 | 按阶段身份完成 / 失败，保护深度禁止内层开放取消 | 三项嵌套阶段 RED → GREEN；截图与取消回归 |
| 业务完成但最终记录无法保存 | 丢失结果或开始下一笔后覆盖内存 | 原结果保留、阻止新任务；“只补存原任务记录”只写记录及索引 | 计数断言；刷新 / 窄屏浏览器 |
| 无法确认停止，记录又保存失败 | 降级为普通失败导致安全语义丢失 | 保持 STOP_UNCONFIRMED 与锁；补存不能解除停止不明 | task-durability；已有进程树测试 |
| 请求在服务登记前就丢失 | 界面只查询不存在任务，无法继续 | 提供保持相同标识 / 完整参数的显式重送；不自动重建请求 | 浏览器 abort 首次 POST，断言原参数及单笔交付 |
| 多工作台实例同时登记 | 两笔业务任务可能同时进入登记 / 审计层 | 跨实例短期登记锁，锁内重新读取原任务 | 两个 Tasks 实例竞争，只有一个回调进入 |
| 旧页面取消 / 修改另一笔交付 | 部分操作遗漏身份判断，前置核对与写锁间有窗口 | 包含取消版本；写锁内再核对 deliveryId | action-boundaries |
| 旧页面开始同步，队列目标已变化 | 开始了用户未选中的目标 | start 冻结 expectedTarget，锁内不符则 QUEUE_CHANGED | 实际 Git 夹具 |
| 发起、Issue / 冲突 / 接收记录操作耗时 | 同步 HTTP 8 秒等待可能超时，结果不明 | 统一后台任务和状态查询，页面不重复提交 | 原连续 / 版本旅程及新恢复旅程 |
| 接收记录表单迁移到后台任务 | 原始 Issue 字段未移除，被受限参数校验拒绝 | 只提交交付身份与 observations；冲突编辑返回其原交付身份 | 连续旅程先复现 INVALID_TASK_INPUT 后通过；版本冲突回归 |
| 任务缺状态 / owner，索引文件指向丢失记录 | 误认已完成或空历史 | TASK_UNREADABLE；显式请求归属另一绑定则 TASK_BINDING_CHANGED | task-record-validation |
| 台账状态未知 / 重复身份 / 活动身份悬空 | 原任务可能被跳过，或页面误展示可审核 | 校验状态、身份、base、candidate、已检查引用及接受 SHA | ledger-boundaries |
| 配置、台账或规则为 null / false / 数字 / 数组 | 可解析但被当成空配置 / 默认规则 | 仅文件确实不存在才首次配置；已有不合规文件保留并暂停 | config-shape / state-shape |
| 私有配置在仓外，手写 stateDir 在安装内 | 私有对象或台账进入安装 / Git 范围 | 正式配置入口独立核对 stateDir；明确备份迁移方法 | private-state-location |

跨实例登记用例复现的是两笔测试业务回调同时被接纳；不把它描述成已发生真实重复 PR。实际 Git 写入另有原台账单写锁。本轮是在该保护上补齐任务登记层。

## 保留并回归的边界

SSH 主机与端口不推断网页 origin；精确网页范围、候选 ref、人工旧引用、配置版本仍需核对。原子替换仍只有限重试同一次 rename，保留旧文件；不会通过重试业务或删除目标文件来规避占用。

原连续模式覆盖共享 Issue 的不同交付、误关检查、实际 main 接受范围、原始提交可达性与内部 merge。原版本模式覆盖共同 README 冲突、内部独有目录、二进制、标签移动 / 回退、上游新增保留路径、检查失败及内部 main 变化。旧任务、请求参数变化、进程树取消和未知停止继续拒绝猜测接管。大量文件继续用折叠目录树 / 搜索 / 分页。

## 验证与产品使用

本轮新浏览器旅程运行正式 createReceiverServer，使用隔离合成 Git 仓与接收 hook：丢弃登记前请求 → 保持同一标识重送 → 实际候选推送并创建单个 PR → 注入最终记录 rename 故障 → 刷新仍显示补存 → 修复占用后只补存 → 撤销自动引用 → 原回执不得恢复 → 补登记现有对象 → 实际 Git 合入并核验。截图只含合成数据；桌面与 390 宽度检查无横向溢出。

检查命令在 packages/repo-sync 运行：node --test test/*.test.mjs、npm run test:browser、node scripts/check.mjs，以及仓库 Biome / diff 检查。最终结果见同包 VALIDATION.md；包含 npm pack 的独立 consumer，正式制品不包含测试 hook、旧原型或 demo 服务。

真实试用只启动 setup/serve；启动不执行 Git，不预置数据。当前页面按钮负责发起和恢复，PR 仍在平台正常审核合入。Agent 不参与确定性比对或同步执行，也没有推送 / 合入 MCP 权限。

## 声明边界

这些检查防护具体可复现的故障，不声称穷尽所有异常。Windows 共享占用及回执丢失采用确定性注入；正常推送和合入执行真实 Git。没有真实内部平台访问，Git push-options 的平台兼容、Issue 关单策略、实际构建与安装仍需使用方验证。Git 回执与 ref 核对不是平台 PR 属性 API 验证。

补存只能恢复当前执行器持有的原结果；强制终止可丢失该内存结果。配置、记录与平台仍不是跨系统事务，也不承诺所有文件系统掉电持久性。直接调用低层 SDK 的信任边界不同于正式配置入口；私有目录检查不是通用文件系统沙箱。

作者验证交由维护者独立审查，不构成审批，不自行合入或发布。公开提交和说明不含实际仓库地址、配置、台账、内部内容、凭据或原始日志。
