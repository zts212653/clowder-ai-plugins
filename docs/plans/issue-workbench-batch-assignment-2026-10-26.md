# 一次性 Open Issue 批量派工

来源：thread_mucwsgsjtlbabfcq#0001793029470179-000018-8a39ac4a；原 Task 继续持责，PR80/feat/issue-workbench 从65b131b接续。

Before：逐条找 Open Issue、看分类、选人、确认，难以比较整批分工。
After：生成当前启用来源的完整 Open 快照 → 复用当前分类/补齐猫研判 → 在统一看板比较和调整成员或本次跳过 → 一次确认 → 持久执行与逐条结果。

- 保留七人名单、OS硬筛选、职责/提交者/Feature/类别/权重的已接受优先级；准备时用虚拟配额累计后续推荐，避免整批都推荐同一人。明确改选不伪称自动推荐。
- 所有 Open 都列入快照，包括已有负责人（默认保留、不能覆盖）。当前无合格分类/系统/成员的条目明确待分析或待处理；可补齐研判或本次跳过，不静默漏掉。
- 准备与刷新只读 GitHub；补研判可发给已配置猫，但不触发自动派工。已进入批次的 Issue（含跳过、停止）不被既有后台自动派工抢先处理；后续可新建批次或主人单条确认。
- 个别调整包括成员选择和本次参与/跳过；源分类/系统仍用原工作台编辑并保存，刷新看板后采用。没有偷偷覆盖人工作品。新开的 Issue 不自动加入已确认快照。
- system 是批次、派工记录及公开内容的发起标识，真实操作人/确认权限留审计；不篡改 GitHub Issue 作者或伪造评论账号。按已声明默认解释执行，不涉及独立机器人账号。
- 批次产生的公开派工、详情与收件不显示邀请 Issue 提交者合入前验收的建议；其他历史记录保持真实。

## 状态与权威

新增 AssignmentBatch 属于插件持久 store（无 TTL）；GitHub Assignees 是外部认领真相，原 DispatchRecord 是每条写入/去重事实。批次记录有 owner、来源快照、revision、逐条人选、来源与策略摘要、结果记录ID。

状态：draft（可编辑）→ analyzing（可停止；只做分析）→ draft → running（确认绑定当前 revision 后不可改人）→ completed / partial。partial 只重试未成功的原意图；需要换目标或原文/策略变动时停止该批次，准备新批次。cancelled 不撤销已成功的 GitHub 写入。恢复读取已保存确认，不把页面重载当确认。

确认前全量复核所选条目的当前来源、已有负责人和成员策略，失败则零写入并要求刷新。每条实际写入再走原权限与策略校验。稳定派工记录ID支持断线重启与重复确认；未知评论结果只查 marker，不盲目重复发布。成功条目不重做，执行采用既有 Host schedule，单次处理有界。

## 实施/验收

1. 后端批次计划、保存调整、补分析、确认/恢复；原生 owner action，不新增猫侧授权入口。
2. 复用现有暖色/组件，看板有范围、状态汇总、成员分布、逐条分类/系统/理由/人选、统一确认与结果；关闭重进恢复。
3. system 标识贯穿公开内容/记录，批次禁止提交者验收建议。
4. 先红后绿覆盖准备零写入、编辑/重复确认、全量预检、权限/成员/OS/source变化、已有认领、加权分配、重启/未知发布、自动分析不派工。
5. 当前仓命令：包 pnpm lint / pnpm test / pnpm build；打包 Playwright 流程与隔离Host实页。git diff --check。真实成员批量写入留给用户在完整看板确认，不在开发验收中触发。

Architecture cell：既有 Issue Workbench team；Map delta：新增该 cell 的持久批次协调对象，复用 DispatchRecord/分类/Host调度，不新增Host权限或第二套Task。tips_exempt：独立插件入口与说明随页面和双语README交付。

实现选择：按创作位消息 `0001793029821146-000022-183f7d7e` 采用分桶、成员分布、逐条调整及恢复状态；入口提升至顶部工具栏，批量方式固定为设置负责人。存储内去重共享成员选项，避免数百 Open 重复名单撑满 Host 单值 1 MiB；准备/确认共用各自的新鲜组织快照，写入仍逐项实时复核。
