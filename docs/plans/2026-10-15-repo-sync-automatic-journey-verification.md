# 自动同步与可选提交重写：作者验证

本次变更继续交付到插件仓 PR #77 的现有分支，未拆分、未合入。原始诉求是初始配置后一次发起同步，用户只在平台审核合入；正常无 PR 主干提交自动纳入，异常留在同一流程并可恢复。

## 实现与边界

| 使用场景 | 实现与验收依据 |
| --- | --- |
| 无 PR 的主干提交 | GitHub 关联清单明确返回空数组时自动纳入，标明独立主干提交。缺失响应、多义关联、错误边界仍拒绝；不伪造 PR。 |
| 点击同步到待审核 | 持久轮次串联扫描、Issue 创建或复用、候选构造、项目检查、推送、PR 创建与回读；只有配置真实自动适配器时提供全自动能力。 |
| 人工合入后 | 服务观察目标分支，实际变化才通过同一个 Tasks 执行器恢复。合入归属、文件树与历史核验后，按全部 required targets 处理 Issue 并回读，再开始下一笔。工具不自动 merge。 |
| 失败、刷新与服务重启 | 原轮次、冻结目标、候选和对象意图保留；结果不明先查原对象，不能重复创建。后台不依赖浏览器。服务重启缺会话认证时需要补充认证再恢复。 |
| 提交身份 | 原对象保留与统一内部身份重写均可选。作者、提交者与推送账号分别解释。身份按交付冻结，候选发布前保存逐条 SHA 映射，关单使用内部 SHA 核验。 |
| 复杂 Git 历史 | 真实 merge 拓扑、精确消息字节、日期、声明路径的内部内容均纳入重写验证；重复构造 SHA 确定。保留模式去掉冗余基线节点。 |
| 配置与隐私 | GitHub 读取 Token 出现在初始仓库配置。Token 分路提交，只存当前服务内存或已有启动环境，不进入草稿、配置、记录、URL。保存后绑定发生变化时，禁止向新绑定提交原 Token。 |
| 当前与历史流程 | 五阶段在同一流程内，完成阶段自动折叠，当前阶段展开；可以主动展开历史。跨两笔交付的同一恢复任务按步骤归属过滤，避免混入另一笔。 |

源码位置：`packages/repo-sync/src/automation.mjs`、`sync-service.mjs`、`commit-policy.mjs`，以及原 Receiver / Tasks / Issue 生命周期和 `packages/repo-sync/web/`。没有修改宿主、全局契约或目录发布条目。
