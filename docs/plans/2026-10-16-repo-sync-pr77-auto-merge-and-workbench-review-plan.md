# PR #77 新反馈审视与优化方案

本方案已获用户批准，实施沿用 PR #77 的现有分支，不拆 PR。实施与验证见同目录的 `2026-10-17-repo-sync-pr77-implementation-and-validation.md`。

## 1. 依据、现场与目标

- [自动合入反馈](https://github.com/zts212653/clowder-ai-plugins/pull/77#issuecomment-6218102150)：CI 尚未完成便报错，手动恢复后又能合入。
- [11 项界面反馈](https://github.com/zts212653/clowder-ai-plugins/pull/77#issuecomment-6218489975)：配置与进度混杂、输入和保存不清楚、排版拥挤、阶段重叠，以及节点可视化。
- 代码锚点：`009f2a10a82d7c93331b2527d4c8a4bc9fdf2b22`；远端 PR HEAD 与本地 HEAD 相同。本地另有上一轮未提交的折叠、摘要及测试修改，须保留并纳入最终回归，不当作已交付。
- 本轮实际核对了评论和源码。访问 5220 返回连接被拒绝，未重启服务，未复现用户内网现场；以下“确认”指可由源码证明的机制，现场时间线来自用户实测。
- 沿用[既有用户旅程方案](2026-10-15-repo-sync-ux-journey-optimization-plan.md)及[开发历史与恢复边界](2026-10-16-repo-sync-development-history-and-retry.md)。本方案修订其 UI 与自动合入部分，保留单向接收、核心一致、内部路径保留、逐条开发提交与 SHA 映射。

目标：用户进入项目，能直接判断“同步哪一笔、走到哪里、为什么等待、接下来由谁操作”；配置只需理解必要输入和一个主要保存动作；正常 CI 等待由系统继续处理。

Architecture cell：repo-sync 本地执行服务与工作台。Map delta：扩展现有观察和投影，不新增调度服务、消息总线或 Agent。同步、核验、重试均由确定性代码执行。

## 4. 自动合入：等待与恢复契约

### 4.1 状态分类

| 实际观测 | 业务处理 | 第四步显示及动作 |
|---|---|---|
| CI created/pending/running/preparing 等明确过渡态；平台 checking/unchecked | 正常等待，轮次保持 WAITING_REVIEW，不抛业务失败 | 蓝色时钟“等待 CI／平台检查”；显示最新状态和下次检查时间 |
| CI success，当前 head、平台合入条件与冻结交付均核验通过 | 保存合入意图，再调用平台合入 | 蓝色执行态“请求平台合入” |
| CI skipped 或没有 pipeline | 不能单凭此值认定允许合入 | 按已验证的平台能力判断；无足够依据时等待／转人工，不能静默放行，也不把未知说成失败 |
| 缺审批、未解决讨论、草稿、需要手动触发 job | 等待人工条件；可继续只读观察 | 黄色 !，给出具体原因和“打开内部 PR” |
| CI failed/canceled、明确冲突、配置不兼容 | 需要处理，保留原 PR 与意图 | 红色 ×，显示原因、平台入口与恢复按钮 |
| GET 网络错误、429、5xx | 对只读请求有限退避，不改业务结果 | 显示最后成功观测及读取错误；连续失败后提示处理；认证错误直接定位认证 |
| 已发合入请求，超时或回执丢失；返回成功但尚未 merged | 结果待确认，只读查询原 PR | 蓝色“确认原合入请求结果”；不重新创建、不重复 PUT |
| 权威回读确认原 PR merged | 第四步完成；进入第五步 | 第四步绿色 ✓，第五步执行 Git／Issue 核验 |

平台缺字段、不认识的状态不得用一长串 fallback 默认为可合入。以明确的状态分类函数和受支持协议表归一化；GitLab 的 detailed_merge_status 可用时优先，CodeHub 使用已验证字段，缺失标记未知。最终仍由平台强制执行审批与分支保护。

### 4.2 生命周期与数据

- 继续由 `SyncService` 调度：每次只执行一次短观察，释放任务／台账锁，再等待下一次调度；不在锁内循环等待 CI。
- 不新增另一套轮次状态机：轮次仍使用 WAITING_REVIEW；在本笔 `delivery.autoMerge` 扩展 WAITING、INTENT_SAVED、RESULT_PENDING、MERGED、BLOCKED 及原因、观测时间、下次检查、等待截止时间等字段。
- 每份观测绑定 projectId、bindingId、runId、deliveryId、PR 地址、候选 SHA；提交状态更新前重验归属，旧异步回执不能覆盖新项目或新笔次。
- pipeline 的 id／SHA／状态若平台有提供则记录并核对；无法证明属于当前候选的 success 不作为自动合入依据。
- PR merged 的证据独立保存为 `mergeObservation`，包含来源、观测时间及平台实际时间（平台提供才记录）。acceptedInternal 仍只由第五步核验推进，不提前伪造接收成功。
- 新增字段须补 ledger 校验、历史投影、完整迁移包校验和导入恢复；旧记录缺字段时按事实回读，不推断成成功，不改写旧配置快照。
- 旧版本已进入 FAILED 的轮次需要显式“恢复原同步”一次；此后若只是 CI 等待即可自动观察。不能仅凭旧 AUTO_MERGE_BLOCKED 错误码猜测它一定是正常等待。

### 4.3 轮询、超时与审计

建议初值：CI 等待采用 10／20／30 秒退避，之后最多每 30 秒检查；新状态变化后回到较短间隔。429 尊重 Retry-After；普通 GET 暂态失败最多连续重试 3 次后提供处理入口。

CI／平台检查的自动等待默认 30 分钟，可在高级策略修改；超时变成“等待超时，需确认是否继续”，保留 PR，用户明确继续才重置预算。人工审批显示等待时长，不使用 CI 超时去宣告审批失败。合入结果不明时继续只读核对；观察预算耗尽后请求处理，不自动重复写入。

持续相同状态的轮询只更新最新观测和计数，不为每次无变化 GET 新建一份完整同步任务或增加子节点；状态变化、远端写入意图、结果、错误及恢复才形成审计事件。已有历史不得删减。

### 4.4 写入与控制边界

1. 发出合入请求前重新核对开关、原 PR、base/head、候选检查、原分支和平台规则；漂移时暂停，不覆盖或强推 main。
2. 保存 INTENT_SAVED 后才 PUT；返回结果不明进入 RESULT_PENDING。重启先查原对象，未经确认不得重发写请求。明确拒绝且确认未执行后，修复并显式恢复才允许再请求。
3. 用户关闭自动合入后，尚未发出的请求停止；已经发出的请求仍必须回读，不能承诺撤回。界面说明“后续由你手动合入”。
4. “本笔完成后暂停”继续完成本笔合入观察、第五步核验与关单；到边界才暂停下一笔。此按钮不等于取消已发合入请求。
5. 迁移冻结、记录落盘失败、停止未确认、撤销意图等原有门禁继续优先。模板和完整迁入环境均不自动重新授予合入权限。

例：CI 第 40 秒创建、第 49 秒成功时，第四步先显示自动等待；下一次观测成功后请求合入，确认合入才进入第五步，用户不必点击恢复。若 Issue 关单失败，则第四步保持完成，第五步红色 ×，恢复只处理未完成结果。

## 5. 工作台：一套真实状态，一个流程

### 5.1 页面布局

```text
项目侧栏约 264px          项目 A · 同步工作台           当前操作
项目 A  [设置]           当前 PR #… · 第 2 / 8 笔     等待 CI · 自动继续
项目 B  [设置]           开发提交 18 · 落地 1 · Issue 2 打开内部 PR
＋ 新增项目              外部 → 内部 SHA / 目标 tag    本笔完成后暂停
                         ① 范围 ✓                    关闭自动合入
                         ② 准备 ✓
                         ③ 发布 ✓                    历史记录 [8]
                         ④ 平台合入 ◷ 等待 CI
                         ⑤ 接收核验 ○
```

- 不再让“项目栏＋永久历史栏＋正文＋操作栏”四列并存。历史入口在正文标题旁，点击后在同页选择记录并复用流程区；历史只读，返回当前的入口始终清楚。
- ≥1440px 可用右侧约 280px 操作区；769–1279px 使用紧凑的正文操作区；1280–1439px 经实际几何断言改为约 248px 右侧操作区，避免内容过窄；小屏纵向布局，允许滚动，不出现横向溢出或遮挡表单的大面积悬浮框。
- 在 1440×900、1366×768 默认折叠状态下，首屏同时看到当前对象／数量摘要、五主节点、等待原因和主要操作。长名称截断但可键盘聚焦查看完整值，正文保留准确地址。
- 侧栏项目只显示名称、单独一行模式和简短状态，不混排成长句；改名、仓库地址、认证及迁移操作放入设置页。

### 5.2 五阶段及其子节点

| 主节点 | 预先定义的子节点 | 完成条件 |
|---|---|---|
| ① 确认同步范围 | 两侧连接／分支检查；准备对象目录；读取两侧对象；目标／基线关系；读取 PR／Issue 来源；冻结本笔交付及台账 | 来源集合完整、本笔范围已登记 |
| ② 准备代码与 Issue | 创建／复用 Issue；逐条构造提交并保留内部路径；候选检查 | 需要的 Issue 和候选检查完整 |
| ③ 发布分支与创建 PR | 发布意图；推送候选；ref 回读；创建／回读 PR；关联 Issue 并回读 | 本笔原 PR 及关联核验通过 |
| ④ 平台审核与合入 | 等待 CI／平台规则；等待人工条件（如需）；自动请求合入（如启用）；确认原 PR 合入 | 有可验证的合入事实，不以请求成功代替 |
| ⑤ 核验与登记接收 | 核验 Git 历史和核心内容；处理应关闭的 Issue；保存接收结果；确认记录持久化 | 接收结果与必需元数据完成，才允许下一笔 |

版本模式将 Issue 节点明确标“不适用”；无 PR 主干提交标明来源类型。逐条 commit 或多个 Issue 的进度显示为某固定子节点内的对象计数，不把每条对象、重试或命令新增成兄弟节点。

第一阶段的本轮来源扫描与每笔冻结需要区分：扫描结果属于本轮，后续笔次引用该证据；不得伪造每笔重新执行了下载。通过版本化计划定义决定适用节点，已确认不适用的步骤标跳过，不伪报完成。

### 5.3 展开、状态与日志

- 五主节点默认全部收起，包括执行中与异常节点。主节点标题直接显示状态、当前子节点名及异常原因摘要；只允许用户主动展开／关闭，同时保留全部展开／收起。
- 按项目、绑定、交付身份保存手动展开状态；同笔轮询、重绘和刷新不改变选择，下一笔从默认收起开始。历史与当前视图不互相污染，扫描阶段状态不泄漏给第一笔交付。
- 绿色 ✓＝完成；红底 ×＝失败；蓝色旋转指示＝实际执行；蓝色时钟＝自动等待；黄色 !＝需要人工；灰色 ○＝未执行。所有状态同时显示文字，不只依赖颜色；尊重减少动画设置。
- 同一串行流程最多一个实际执行主节点。第四步确认合入后变绿，第五步才运行；第五步失败不让第四步退回“核验中”。“观察到 main 变化”尚不能证明原 PR 已合入。
- 点击节点在同页展开子节点；点击子节点在同页查看输入输出摘要、外部／内部对象、时间和恢复动作。技术执行详情默认隐藏，不开新窗口；真实 PR 链接仍跳具体平台地址。
- 面向用户默认展示结果，例如“已重放 18/18 条提交”“关联 Issue 2/2”“CI running”；任务 ID、Git 下载统计、命令层证据和尝试记录只放“技术详情”。不删除审计能力。

### 5.4 单一投影

以现有 `recording.phaseLocation`、`taskPlan` 和 `web/step-plan` 为入口收敛为一个版本化流程契约：阶段 ID、节点 ID、适用条件和事件归属由同一来源定义，前端消费服务端提供的计划与投影；不再维护几套独立 switch。

为 merge-intent/platform-merge 明确归属第四步，接收核验归属第五步；父包装任务跨阶段不算当前执行节点。节点／摘要／操作栏／历史使用同一投影结果，并保留旧记录的原始归属和“未记录”说明，不重写历史来凑齐新节点。

## 6. 设置：必要输入、只读摘要与一个保存入口

### 6.1 首次配置

保留“连接与认证 → 核验同步起点 → 确认启用”三个真实步骤，每次仅展示当前步骤；进入起点核验后，仓库连接仅保留简短只读摘要。

| 分组 | 用户主要输入 | 自动处理／按需展开 |
|---|---|---|
| 项目 | 名称、同步模式 | 名称不影响绑定及已有历史 |
| 外部 GitHub | 仓库地址、来源分支；过程模式所需读取 Token（无可用认证时） | 分支提供默认值但可修改；版本模式不展示无关 Token 输入 |
| 内部仓库 | Git 地址、目标分支、平台仓库／Issue 页面链接、平台 Token（无可用认证时） | 从已支持的链接结构推导项目路径及 API；Git URL 与网页不同才补网页地址；不能可靠推导时才展开报错字段 |
| 接收策略 | 保留原身份或统一身份；重写时填姓名／邮箱 | 保留路径在下一步文件树选择；高级 API 覆盖、环境变量方式放一层高级设置 |

每项明确标注“必填／已有值可沿用／自动推导”；示例与帮助各不超过一两句。推导后的 API 接收域名和项目路径以只读摘要可见，用户提供 Token 前可核对；更改接收域名不得携带原 Token 自动发送。

唯一主要动作“保存并验证连接，继续 →”：字段校验 → 保存非敏感配置 → 会话提供认证 → 只读检查 → 当前区显示结果 → 起点核验。只读通过不声称拥有创建／合入权限，也不为验证创建测试 Issue／PR。

### 6.2 已启用设置

按以下分组展示，移除初始化步骤条和“配置已完成”大卡片：

1. 项目基本信息：名称与模式；改名在此操作，模式／仓库绑定按已有规则冻结。
2. 仓库与接收起点：外部／内部地址、分支、初始与当前对应、文件保留规则，清楚显示哪些只读。
3. 认证与自动化：GitHub 和内部平台认证状态、替换 Token、创建方式与实际 API 接收范围。过程模式共用内部 PR／Issue API，不重复填一套接口。
4. 提交与接收策略：展示本笔冻结身份及项目设置；活动交付期间只读；自动合入的本轮开关和暂停边界在工作台操作区直接可达。
5. 导入导出和诊断：复用已有迁移功能，默认折叠为一个明确入口。

页面提供一个“保存设置”主要按钮，并明确列出修改范围；不可编辑字段不进入请求。保存成功不自动开始新同步；从原错误跳来的恢复入口保存并验证后回到同笔，由用户明确继续。

统一保存采用专用配置协调入口（拟新增），不经会落盘业务输入的 `/api/tasks`。在现有项目配置锁内校验 projectId／bindingId／expectedRevision，拒绝冻结字段变更；非敏感配置仍沿用原私有配置写入机制。认证继续走服务内存边界，响应逐项报告配置保存、认证提供和只读检查结果；不得将包含 Token 的原始请求交给任务输入、审计、错误详情或草稿捕获。

Token 仅写服务内存。统一按钮不意味着把密钥与配置落入同一持久文件：如果配置已保存但认证提供或验证失败，必须显示分阶段结果“配置已保存，认证待处理”，定位失败分组，不能显示全部失败或假报全部完成。revision 冲突在任何写入前拒绝陈旧提交，避免改到别的项目。

“验证连接”为只读辅助动作，不是另一种保存；“清空输入框”只清尚未提交的文本；撤销已提供的会话 Token 单独标“移除本次服务认证”。目前“清除本次输入”实际还请求删除服务内存 Token，必须同时校正文案和操作语义。

### 6.3 Git PR 选项与兼容

新建界面默认 API 自动创建，移除 Git 推送 PR 选项及 push-options 教程；代码仍通过标准 Git push 提交。内部平台 Token、项目路径和 API 推导失败就定位具体字段，不再让用户先理解 GitLab 产品名。

已有 git／command／manual 配置和历史仍能读取、导入和定位原对象；进行中不能静默改传输或丢掉已发布意图。旧项目显示“旧创建方式”及当前值，在安全边界提供显式切换 API 的配置路径；已有 PR 先完成或核对，不自动另建。只有确认无兼容存量后，才另作底层删除评估。
