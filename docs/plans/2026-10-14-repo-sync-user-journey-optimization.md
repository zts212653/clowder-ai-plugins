# 仓库同步插件：用户旅程与流程界面优化方案

本文件整理自用户对 PR #77 的交互反馈和当前对话中的优化建议，用户确认后的实施依据。代码已在 PR #77 的现有分支落地；实施记录与技术验证见第 11 节，目标用户可用性探索不等同于自动化测试。

本轮已对 [设计复审与实施建议](2026-10-14-repo-sync-ux-review-and-recommendations.md) 逐项核对，成立的建议整合到正文，调整或不采纳的理由见第 9 节。复审原文保留，本文件承载处理后的统一方案。

## 1. 背景与问题

用户期望从一笔同步的开始到结束，在同一个流程中看清大步骤、所属子步骤、执行结果和下一步操作，并能点击历史版本或 PR 回看当时的完整过程。

当前主要问题：

1. 大步骤、后台执行步骤与执行记录分散展示，用户需要自己把它们对应起来。
2. 历史主要是折叠文本，缺少可直接进入的完整同步详情，以及步骤时间和当时配置。
3. 下一步按钮位置、文案和入口不统一，经常需要寻找。

现有验证更偏向执行正确性，还不足以证明用户能够自然、连续地完成整个旅程。本轮优化围绕真实操作路径组织页面，而不是继续增加独立提示卡片。

## 2. 设计目标与保持的业务边界

页面主线统一为：**选择一笔同步 → 查看完整流程 → 完成当前步骤**。

当前同步和历史同步使用同一套详情界面，执行记录嵌入所属步骤，操作位于固定区域。

保持已有两种模式：

- `continuous`：按外部 main 的实际 PR 落地范围接收原始提交对象，登记 Issue 和 PR 来源关系。
- `version`：按冻结 tag 更新内容，保留声明的内部文件、合并共同修改文件，只产生一个内部同步 PR。

保持单向外部接收、真实 Git 核验和正常内部平台审核流程。打开具体内部 PR 仍跳转到平台地址。Issue 在平台创建与核对，工具记录映射和接收结果；Agent 不承担确定性比对、推送或合入。

## 3. 页面结构

### 3.1 工作台布局

```text
仓库名称 · 同步模式                          仓库设置
当前已接收版本：外部 v2.3 → 内部 commit I1
更新状态：与最近一次扫描一致 · 扫描时间……

同步记录                         本笔同步详情
──────────────────              ─────────────────────────
当前：v2.4 · 文件冲突             v2.3 → v2.4
                                外部 U0 → U1 / 内部 I0 → 待接受
历史：
v2.3 · 已完成                    ✓ 1 确认同步范围
v2.2 · 已完成                    × 2 准备代码        ← 当前展开
PR #123 · 已完成                    ✓ 核对文件规则
                                  × 合并 README.md
搜索 / 状态 / 时间筛选               ○ 执行项目检查
                                ○ 3 发布候选与创建 PR
                                ○ 4 内部审核合入
                                ○ 5 核验并保存结果

                                当前需要：解决 README.md 冲突
                                [处理文件冲突]
```

以上版本、PR 和 SHA 名称仅为布局示例，不是实际仓库数据。

### 3.2 仓库摘要

顶部展示仓库身份、同步模式、当前已接受的内外版本对应、最近扫描目标和扫描时间。

“与最近一次扫描一致”不等于已经重新检查了实时上游。扫描过期或未扫描时明确显示时间或“尚未检查更新”，避免误导用户认为已经是实时最新版本。

代码接收状态与记录保存状态分开。例如：“代码已接收，记录待保存”。

### 3.3 同步记录列表

左侧固定展示当前同步与历史记录，支持搜索以及状态、时间筛选。列表项展示版本或来源 PR、同步状态和关键时间，点击后在右侧查看该笔详情。

记录列表采用分页或增量加载，历史详情按所选记录加载。新任务的轮询只更新相关记录与步骤，不在每次刷新时读入全部历史任务或重建整页。

已撤销、失败或未完成的记录也应保留可辨认的状态，不能仅凭相同 tag 标题混为一笔成功记录。

历史浏览期间，后台刷新不强行切回当前任务；顶部保留“当前同步正在执行，返回查看”的入口。返回时保留用户选中的记录和展开位置。

### 3.4 首次接管与仓库设置

首次使用保留独立仓库接管向导：配置连接 → 读取版本 → 核验 U0 / I0 → 登记基线。完成后进入同步工作台。

首次状态按配置与台账判断，而不是按历史同步条数判断。无配置时连接仓库；有配置、无基线时登记已有基线；已登记基线但尚无交付时直接进入目标发现与确认。启动继续保持不自动执行 Git，不在未扫描时展示虚构的最新版本。

已有两仓、内部落后多个提交时，向导必须明确填写上次已接收的外部 U0 和内部当前 I0，并展示两者的对应关系。

仓库设置继续承担管理职责；同步中允许补填的必要字段，例如内部网页地址，在阻塞的当前步骤内提供入口，减少往返和上下文丢失。

选择目标与确认范围是不同动作。version 可以选择符合现有历史、标签与文件规则校验的后续 tag；continuous 必须按已证明的 main 接受顺序接收下一笔，不能通过任意选择 PR 跳过中间提交。

### 3.5 列表与垂直时间线、移动端适配

桌面采用列表与详情分栏，右侧五个大步骤用垂直时间线展示，子步骤在大步骤内分组。版本对应摘要保持容易访问，已完成内容可折叠，当前展开内容不因轮询反复收起。

分栏宽度按内容适配，不硬性固定 30% / 70%。断点先以约 768 CSS px 作为原型起点，再用长版本名、完整 SHA、缩放和窄屏实际验证；覆盖断点两侧及断点本身。

窄屏采用“列表 → 详情”的同页面视图切换，详情顶部提供“返回同步记录”。返回保留筛选与列表位置，不另开窗口或审批弹窗。操作区支持安全区域、软键盘和长提示，不能遮住表单、错误原因或键盘焦点。

主要触控目标按至少 44 × 44 CSS px 的产品设计目标实现，不只增大按钮文字或高度。Apple 的触控建议使用 pt；Web 规范使用 CSS px，不能直接把两者写成同一条要求，依据见参考链接。

状态同时用文字、图标和语义色表达，不能只依靠颜色或脉冲动画。动效遵从减少动态效果设置；键盘操作、焦点可见和状态播报纳入验收。

## 4. 同一个流程展示大步骤、子步骤和记录

### 4.1 统一的大步骤

| 大步骤 | 子步骤与具体信息 |
| --- | --- |
| 1. 确认同步范围 | 来源 PR / tag、更新范围、U0 / I0 对应、两侧分支、文件变化和本笔配置 |
| 2. 准备代码 | 过程模式登记 Issue 映射；读取对象、构造候选；版本模式保留内部文件、处理三方合并；执行检查 |
| 3. 发布候选与创建 PR | 保存创建意图、推送候选并触发创建、核对回执与候选、登记具体 PR |
| 4. 内部审核合入 | 内部 PR 链接、来源 / 目标分支、等待合入状态 |
| 5. 核验并保存结果 | 核验实际合入、保存内外版本对应；过程模式确认 Issue 接收记录；保存执行记录 |

两种模式共用流程结构，但只显示适用的子步骤。版本模式不显示 Issue 搬运和接收步骤。

“准备代码”进一步分为来源对象与映射、内容处理、检查结果三个阅读分组；这些是展示分组，不增加一套独立业务状态机。continuous 在 Issue 映射就绪后准备原始对象候选；version 先读取与处理内容、解决合并，再生成候选，不能照示意图把候选构造提前到内容合并之前。

检查结果只展示实际配置或实际执行的检查。默认 `git fsck` 不等于插件兼容性或业务测试。未配置这些检查时明确说明“当前仅执行 Git 基础检查”，不展示虚构的通过结果或必然会执行的等待项。

Git 自动 PR 路径中，推送候选与触发创建发生在同一次 push。界面应如实表达，不拆成两个虚构的独立平台动作。

该步骤可展开为：保存创建意图 → 推送并触发创建请求 → 提取创建回执 → 回读候选 ref → 登记 PR 引用。推送成功不单独证明 PR 已创建；缺回执、多个回执或 ref 不符时进入原对象核对路径，不能重复创建。

展示受限操作摘要、真实来源分支、目标分支、候选 SHA 和证据来源。原始命令、完整 argv、推送回显及未经处理的输出不进入网页或历史。Git 回执与 ref 核验不冒充平台 PR 属性 API 核验。

### 4.2 子步骤详情

每个子步骤可直接展开，查看：输入摘要、结果、开始时间、结束时间、耗时、执行尝试及固定脱敏错误。

后台任务归到其所属大步骤和子步骤，不在流程外另建一套任务面板。详细执行信息仍可折叠，默认突出业务结果。

一次失败后重试，保留“第一次失败、第二次成功”的时间与结果，不覆盖原尝试。同一请求的查询或同标识重送不冒充新的一笔同步。

一项后台任务可能覆盖多个大步骤，例如 prepare 同时涉及准备、发布和 PR 核验。应按稳定的执行阶段标识关联子步骤，而不是强制一个 taskId 只属于一个大步骤，也不解析中文日志文字来猜归属。

### 4.3 状态规则

| 状态 | 含义与展示 |
| --- | --- |
| 待执行 | 尚未到达的步骤，保持可见但不表示失败 |
| 正在执行 | 当前真实执行的子步骤，显示阶段进度或耗时 |
| 等待操作 | 需要填写、解决冲突或在平台审核，明确由谁完成什么 |
| 待核对 | 外部结果尚未确认，给出原对象的核对入口 |
| 已完成 | 已取得该步骤所需结果，可以展开查看依据 |
| 失败 | 显示 ×，原因和处理入口位于对应子步骤下 |

当前步骤自动展开，已完成步骤默认折叠，后续步骤保持可见。失败只标记实际失败的步骤，等待平台合入不能统一显示为失败。

嵌套核验与执行记录保存必须正确归属。例如 PR 回执核验内部的连接检查，属于该次核验的执行详情；记录保存失败属于“核验并保存结果”，不能让已完成代码接收显示为尚未执行。

## 5. 历史同步详情

### 5.1 可回看的内容

点击历史版本或历史 PR，进入同一套流程详情，展示该笔已经记录的过程和结果。

| 信息 | 内容 |
| --- | --- |
| 版本对应 | 同步前后外部 tag / commit、内部基线、候选 commit、实际接受 commit |
| 对象对应 | 外部 PR、内部 PR、Issue 映射及已记录的接收状态 |
| 时间过程 | 各步骤执行时间、失败与重试、首次观察到合入的时间、完成时间 |
| 文件结果 | 更新文件、内部保留路径、共同修改文件和冲突处理结果 |
| 当时配置 | 两侧仓库与分支、同步模式、文件规则、PR 创建方式和检查策略摘要 |
| 执行依据 | 区分 Git 核验、创建回执、平台接口回读和操作者登记 |

内部没有实际 tag 时，显示“未设置内部 tag”及对应 commit，不把外部 tag 当成内部已有 tag。原始提交对象、内部候选与实际接受 commit 分别展示，避免误把不同概念合成一组相同 SHA。

### 5.2 时间与配置的真实性

工具首次观察到合入的时间，不等于平台实际审批或合入时间。缺少平台数据时按观察时间标注，不推断批准人或审批详情。

历史详情展示该笔当时生效的配置，而不是当前配置。允许的后续补填，例如网页地址，作为变更历史追加，相关步骤展示当时实际使用的版本。

历史中未保存的字段显示“当时未记录”，不能猜测或用当前值回填。

历史配置只保存可追溯所需的受限字段和检查摘要，不包含凭据、完整原始配置、未经筛选的命令参数或原始 Git / 平台输出。

### 5.3 需要补齐的记录结构

历史回看不能只做前端排版，需要补齐以下关联：

1. 一笔同步有稳定的同步身份，包含来源、冻结范围、内外基线及最终接受结果。
2. 一笔同步关联多个执行任务；任务通过明确身份归属，不能只按时间靠近来猜。
3. 执行任务关联所属大步骤、子步骤及尝试，保留时间和结果。
4. 本笔配置快照与允许的配置变更可追溯，步骤可引用当时生效版本。

连接、初始化和首次基线核验等尚未产生同步身份的任务，归属仓库接管过程，不强行附到后面某个 PR。查看历史时读取该笔的记录，而不是只展示最近一次后台任务。

### 5.4 最低交付要求与渐进存储策略

可以增量补字段、使用扁平 JSON 和受限读取投影，不要求一次引入多表或重写现有执行器。但本次完整交付必须具备同步与执行阶段的明确关联、失败尝试、历史时间和当时配置摘要，不能把这些必需内容推迟到另一次交付。

保留现有台账与执行记录作为业务依据，历史界面读取统一投影，不另外维护一套独立推进的同步状态。候选、基线和接受结果来自冻结 delivery 与真实核验，不能从当前 config 或当前游标重新推断过去。

映射按集合保存，不能将多个 Issue 和原始 commit 缩成一个编号或一个 SHA；平台对象保留稳定身份与完整有效链接，展示编号不假设只能是数字。时间以 ISO 8601 字符串保存，业务状态、任务状态和记录保存状态分开，保留等待、结果不明和停止不明等语义。

候选完整性检查、远端 ref 回读和实际合入核验分别记录。`git fsck` 不等于候选 ref 已回读，操作者声明已合入不等于工具已经核验并接受，不能仅换一个 evidence 标签就产生已接受状态。

### 5.5 旧数据、版本与持久化

新记录使用显式 schema 版本与字段校验；旧格式只能按已知旧结构识别。未知版本、损坏文件和不完整状态保持暂停，不按“缺 configSnapshot”或“缺 tasks”自动当成可迁移旧数据。

旧记录可以只读投影为统一界面：显示能够由已保存内容证实的字段，缺失部分标为“当时未记录”。读取不自动覆盖源文件，不用当前配置补快照，不按时间邻近或相同 tag 猜任务归属。需要写入迁移时先备份、核对绑定并提供失败恢复。

新增快照或索引复用现有写锁、原子替换和原任务身份规则，明确部分写入失败时的恢复。不能假设多个 JSON 文件的分别原子写入形成跨文件事务。只补存派生记录不重跑 Git、候选发布或 PR 创建。

清理旧 UI 不等于删除旧数据读取兼容。兼容范围与支持的数据版本单独说明，不能因新页面测试通过就移除已有用户台账的读取路径。

## 6. 固定的下一步引导与操作区域

详情顶部始终回答：本笔接收什么、现在进行到哪里、接下来需要谁做什么。

主操作位于固定区域，长页面滚动时仍能找到。随当前状态切换按钮与说明，避免多处重复主按钮。

使用详情内的固定操作区或经滚动容器验证的粘性操作栏。正文预留足够空间，验证首屏、末尾、短内容、窄屏、软键盘和缩放；不直接把 `position: sticky; bottom: 0` 视为任意结构下都能常驻的保证。

同一视图只有一个主要业务推进按钮。步骤内可以提供定位或展开链接，不再复制同一个主按钮。主次样式与状态色复用、扩展现有语义变量，复审中的蓝色、阴影和具体 CSS 是示意，不直接覆盖现有主题；不因示例中有“删除”样式而新增历史或平台对象删除能力。

| 当前情况 | 提示 | 操作 |
| --- | --- | --- |
| 尚未选择目标 | 选择本次要接收的版本或 PR | 选择同步目标 |
| 范围已确认 | 将接收这些变更，内部 main 等待平台合入 | 开始同步 |
| 正在执行 | 正在下载或检查，暂时无需操作 | 显示执行状态；仅在允许阶段提供取消 |
| 文件冲突 | README.md 尚未解决，候选未发布 | 处理文件冲突 |
| 缺少网页地址 | 填写内部仓库的 HTTPS 首页 | 补填网页地址 |
| PR 已创建 | 在内部平台完成审核合入 | 主操作打开具体 PR；提供合入结果核验入口 |
| 等待合入核验 | 已在平台合入后回来核验 | 核验合入结果 |
| 记录保存失败 | 业务已结束，只需保存原记录 | 补存执行记录 |
| 本笔已完成 | 展示接受版本和完成时间 | 查看下一笔更新 |

按钮必须根据真实交付、任务、记录状态及当前所选身份共同判断。“待执行”不自动意味着允许开始同步，“失败”不统一提供重试，“当前步骤完成”不允许通过纯 UI next-step 绕过后端条件。未覆盖状态只展示核对与帮助入口，不默认返回继续或重试按钮。

| 异常或特殊状态 | 允许的处理 |
| --- | --- |
| 普通连接失败 | 原因核对后重新检查连接；不假设候选或 PR 未发布 |
| 文件冲突 | 进入具体文件处理，完成后按原交付继续检查 |
| 创建回执丢失或推送结果不明 | 核对原 ref / 已创建 PR，保持原意图；不重新创建 |
| 人工引用被撤销或纠正 | 尊重原纠正结果，补登记核对后的现有对象，不用旧回执覆盖 |
| 原结果待补存 | 只补存原执行器持有的记录；展示实际业务状态，不把所有 TASK_STORE_FAILED 都写成“代码已接收” |
| 停止不明、任务执行中或记录仍在保存 | 等待、核对原执行器与原任务，按后端允许的阶段取消；不发起另一笔 |
| 已完成的历史记录 | 只读回看、展开证据或打开具体 PR；切回当前入口后再选择下一笔 |

必要表单和文件处理在当前步骤内展开。错误提示先说明原因和处理方法，错误码放在详情中。只有需要平台操作时才跳转到具体对象地址。

完成动作后，原位置明确显示结果，展开下一步并更新操作文案。刷新保留所选记录、展开步骤和未提交草稿；历史详情中的操作必须明确属于所选记录，不能误作用于当前另一笔同步。

返回平台后的目标是原同步详情直接可见核验入口；一次点击提交核验即可，不要求额外导航。仅在用户确实返回原当前同步时成立，正在浏览历史时仍保留历史选择。完成文案按模式展示原始 tag 或来源 PR，不追加固定的 `v` 前缀，也不假设 continuous 存在 tag。

加载时展示可信的阶段、耗时和 Git 报告的对象数 / 百分比；没有数据时用不定进度。百分比只属于对应下载阶段，不代表整笔同步，不展示无依据的“预计还需一分钟”。不可取消时说明当前发布或结果核对边界，不在未确认推送发生时断言“推送已发生”。

记录补存与请求重送的已有保护继续保留：只补存原结果、不重跑 Git / PR；重送保持同一标识和原参数；结果不明先核对原对象；停止不明不解除锁。

## 7. 关键用户旅程与验收标准

| 场景 | 预期旅程 | 验收重点 |
| --- | --- | --- |
| 版本更新遇到 README 冲突 | 第二步显示 × → 进入文件处理 → 保存 → 在原位置继续检查 | 不寻找另一个任务窗口；失败、处理和后续执行均在所属步骤 |
| PR 已自动创建 | 看见具体 PR 与候选 → 打开平台审核 → 返回 → 核验合入结果 | 返回位置明确，不出现模拟审核弹窗，不重复创建 |
| 记录保存失败 | 显示代码已接收、记录待保存 → 补存 → 完整历史 | 业务状态与记录状态分开，补存不重复执行同步 |
| 回看上个月的版本 | 点击记录 → 查看内外对应、步骤时间、重试和当时配置 | 读取所选记录，不使用当前配置或最新任务冒充历史 |
| 已有两仓、内部落后 20 个 commit | 登记上次接收 A 对应的 U0 / I0 → 持续同步 → 历史追溯 | 不把外部最新版本当初始已接受版本，对应关系可追踪 |
| 执行期间查看历史 | 切到历史 → 后台继续刷新 → 返回当前同步 | 不强行跳回当前任务，不丢失历史选择，不让历史按钮操作另一笔 |
| 重试与刷新 | 原失败保留 → 新尝试成功 → 刷新回看 | 时间与尝试可见，选中记录和合法草稿保留 |

验收既检查执行结果，也检查用户是否能直接回答“在哪里、卡在哪、下一步做什么”。仅按钮齐全、接口成功或没有横向溢出，不足以证明旅程成立。

### 7.1 原型可用性验证

在记录关联与新页面实施前，用明确标注假数据的可点击原型验证开始同步、处理冲突、平台跳转返回和历史回看四条旅程。原型是单独的设计验证产物，不接真实 Git / 平台，不进入正式服务、MCP 启动路径或安装制品，不重新引入 demo 服务。

可邀请 2～3 位未参与设计、但符合目标使用者背景的人进行小规模探索，需按实际可获得的参与者安排，不擅自联系或分配任务。记录未经指导的首次动作、找到入口用时、错误点击、求助次数和对状态 / 配置来源的理解。反馈用于修改设计，不把小样本当成总体用户成功率证明。

“3 秒找到冲突入口、10 秒找到开始入口”保留为待验证的体验目标。起点分别为目标状态稳定可见和任务说明结束；记录每人的结果，区分首次使用和熟悉后使用，不作所有用户的硬性时间承诺。完成动作正确、无需设计者解释是比计时更优先的标准。

### 7.2 可以自动或客观复核的条件

- 刷新仍保留所选历史记录；当前任务完成时不抢占历史视图。
- 当前任务的操作区在指定滚动与视口组合下可达且不遮挡内容，同一视图没有重复主操作。
- 平台返回原详情后，核验入口无需额外导航；点击核验不会新建同步。
- 记录失败展示真实业务结果与待保存状态，补存不重复 Git / PR。
- 原失败尝试、后续成功尝试、时间和实际配置版本可展开查询；旧缺失字段不被伪造。
- 连续模式不能跳过接受顺序，版本模式的目标须通过历史与冻结校验。
- 390 CSS px、断点两侧、桌面、键盘操作及放大文本可用；对可获得的真实设备进行抽样，记录尚未覆盖设备。
- 大量文件、多次重试和多笔历史验证分页 / 按需加载；记录刷新、渲染与内存的实际基线，发现退化再优化，不先写无测量依据的性能数字。

保留现有产品执行测试的业务断言，浏览器脚本随新旅程迁移，新增历史关联、受限快照、旧数据和异常操作策略的必要用例。已有 113 项产品测试与 8 个浏览器脚本是此前验证基线，不是保证新改动无风险的依据，也不要求未来测试数量固定不变。

“测试覆盖率达到 100%”不作为完成条件。完成条件是已约定旅程与恢复边界有证据、受影响验证通过，以及用户无需解释就能理解和正确操作。

## 8. 建议实施顺序

1. 确定页面结构、五个大步骤、两种模式的适用子步骤和各状态操作文案。
2. 制作覆盖正常、异常、等待审核、历史详情的同一版低保真交互稿及可点击原型，先验证入口、理解与返回路径，修正发现的问题。
3. 在同一分支增量补齐必需的同步、任务、执行阶段、尝试和受限配置快照关联，明确版本与旧数据只读投影；不新建竞争业务状态。
4. 统一当前与历史详情，按真实数据映射流程；先走通一条代表性旅程，再覆盖连续、版本、历史和恢复。
5. 落实固定操作区域、移动端、选择保持、刷新恢复和平台跳转返回路径，迁移浏览器验证。
6. 完成必要的产品 / 制品和交互验证、确认读取兼容与恢复行为后清理旧渲染代码。所有必需能力在本次同一个 PR 内完整交付。

新旧 UI 切换只可作为隔离开发 / 验证期间的可选手段，不作为正式用户必须学习的开关，也不通过默认旧界面推迟本次交付。若使用开关，由服务端或测试启动参数控制只读界面版本；浏览器入口是 web/app.mjs，不能直接复制复审示例中的浏览器 process.env 或错误文件路径。

迁移期间保持一套执行与写入路径，按风险抽样旧视图，不默认长期维护两套完整测试或用旧 UI 验证代替新 UI 验收。清理渲染代码与保留旧数据读取兼容分别判断。

上述是同一个 PR 的内部实施顺序，不是两次产品交付。复审提出的“本周 / 下周 / 一个月”和固定工期未基于资源、数据量、验证参与者及迁移工作量确认，暂不作为排期承诺。

落地时沿用 PR #77 的现有分支完整交付。后续用户已授权直接开发；本次实施与验证在同一个 PR 中交付。

### 9.1 判断依据与尚需验证的边界

本轮核对了现有 web/index.html、web/app.mjs、web/styles.css、src/server.mjs、src/tasks.mjs、src/task-store.mjs、src/ledger.mjs、src/config.mjs、src/execution.mjs 等实现。可复核的关键事实：

- 主流程和 operation 区域目前分开，任务文件有 bindingId / action / steps，但 deliveryId 仅在执行上下文，缺持久关联和受限配置快照；仅换布局不足以兑现完整历史。
- 台账已有等待审核、推送结果不明、代码接受待元数据等业务状态；Tasks 另外保护停止不明与记录补存。四个通用状态和统一重试不能替代这些语义。
- 正式网页使用原生浏览器模块，资源从 web/ 提供；没有可直接供浏览器使用的 process.env。
- 网页的公开配置与错误是受限投影，已有命令 / 原始输出不公开的合同；增加历史不能逆转这些保护。

这些是方案与实现约束的核对，不是新界面的浏览器验收，也不代表同意所有复审代码片段。布局、断点和操作栏仍需原型与真实旅程验证。本轮不修改复审原文和产品代码。
