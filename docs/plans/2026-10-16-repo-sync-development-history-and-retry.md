# PR 开发历史重放与未合入撤销重做

用户指定上游 clowder-ai PR #1405：PR 有 18 条提交，main 以单父 squash 提交 `7188f737…` 接收；原 PR head `2d93c685…` 与该落点树均为 `41ec6606…`。原实现按 main 实际新增对象重写，因而只有 1 条。用户明确选择内部恢复 18 条开发提交。

## 接收合同

- 过程模式 + 统一身份：对于多条开发提交压成单条 main 落点的 PR，完整读取 PR 提交列表，核对数量、唯一 SHA、冻结 head、实际 Git 拓扑和接收基线。读取失败、不完整或来源变化均暂停。
- 从上游 PR ref 读取真实对象，验证 head 与 API 一致。排除已在 main 接受基线中的对象后，实际 Git 范围必须恰好等于 PR 清单；不把主干的其他工作搬运第二遍。
- 逐条重写 PR 图中的提交，保留消息字节和日期，作者/提交者使用内部身份；声明路径每条保留内部快照。末端核心文件必须等于 main 实际落点，不自动三方合并或追加修补节点。
- main 接受游标仍指向实际落点。PR 开发提交 SHA → 内部 SHA 与 main 落点 SHA → 内部候选分别记录；Issue 接收条件不改成开发分支 SHA。
- 保留身份模式仍保留 main 原始历史；版本模式仍为一次内容更新。已发布候选不自动改写，旧交付的冻结策略和历史保留。

## 用户看到什么

在本笔详情顶部显示外部 PR / 内部 PR、PR 开发提交数、main 实际落地数、本次重放/内部提交数、关联 Issue 数。Issue 直接列编号、标题、普通关联/接收后关闭、内部映射和结果；提交清单提供标题及内外 SHA。大列表可展开，业务摘要不依赖阶段执行证据。

## 放弃未合入 PR 并重新同步

- 显式确认后，在写锁内核对原交付、原 PR 链接、候选分支/HEAD 和 main 未前进；先保存撤销意图并暂停轮次，再关闭原 PR 并回读。
- 已合入或 main 已前进时拒绝撤销，转原合入核验；不回滚 main、不删除分支、不清空历史。
- 关闭回执丢失时，刷新/重启后继续原撤销，先回读原 PR，不创建或重推候选。缺少可证明的 PR 关闭查询能力时明确阻断，不伪造关闭。
- 成功后旧交付保留 CANCELLED 记录，接受游标和 Issue 映射不动，清除待处理队列并暂停。用户明确继续后重新读取同一轮目标，使用新的交付身份/分支/PR，记录对旧交付的替代关系；复用同一内部 Issue。
- 普通“恢复原同步”不能越过未完成的撤销意图。多项目、旧页面和历史记录仍受原绑定/交付身份检查保护。

## 验证

真实 Git 夹具覆盖多提交 squash、普通 merge/rebase、空变更提交、保留路径、拓扑、最终树不符、缺失/变动 PR ref、完整映射和迁移对象。撤销覆盖未发布/已发布、关闭回执丢失、服务重启、重复请求、已合入拒绝、候选冲突与新 PR 复用 Issue。浏览器覆盖业务摘要、具体 Issue、外链、撤销确认和显式继续、历史与移动端。平台 API 测试替身与真实内网验收分开记录。
